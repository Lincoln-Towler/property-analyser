# Property Analyser — Web

The public site, and it's read-only by design: no login, no admin page, and nothing here can change the data. The scoring engine is a pure TypeScript port of the original Python, verified by golden-master parity tests.

## Pages

| Route | Contents |
|---|---|
| `/` | Market score + gauge, confidence interval, four pillar sub-scores, key indicator tiles, auto-generated commentary, score-history sparkline |
| `/indicators` | Config-driven card per indicator: current value, target, status, history chart with threshold line. Single-point indicators show an honest "no trend" card instead of a broken chart |
| `/locations` | Locations ranked by score, regional divergence, head-to-head comparison. Prices are SQM asking prices |
| `/cycle` | Anderson 18.6-year tracker (anchored **2008**, same as the score — Year 18/Crash as of 2026) |
| `/btc` | BTC signal, price ladder, context flags, latest Cowen summaries, recent automatic flag changes |
| `/audit` | Automation health, per-indicator freshness, point counts, source split, staleness flags (>90 days), property data quality |
| `/api/snapshot` | Cron endpoint, not public: needs `CRON_SECRET`. Computes today's score and upserts into `market_score_history` |

## Local dev

```bash
cd web
npm install
cp .env.example .env.local   # fill in the Supabase URL + anon key
npm run dev
```

Without env vars the pages render a setup notice (and `/cycle` still works —
it's pure computation).

## Tests

```bash
npm test        # golden-master parity tests plus unit tests
npm run typecheck
```

`tests/fixtures/golden.json` was generated by `tests/generate_fixtures.py`,
which runs the ORIGINAL Python scoring functions
(`legacy/property_analysis_dashboard.py`) against synthetic SQLite datasets
(`python3 tests/generate_fixtures.py tests/fixtures/golden.json` from `web/`).
The TS engine must match those outputs exactly — including
two known quirks preserved deliberately (see the PARITY NOTE in
`src/lib/scoring/engine.ts`). If you change scoring behaviour on purpose,
regenerate fixtures and land the change as its own commit with the score
delta recorded.

## Deploy (Vercel)

1. Import the repo in Vercel, set **Root Directory** to `web/`.
2. Env vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET` (any random string).
3. `vercel.json` schedules `/api/snapshot` daily at 21:00 UTC (~7am AEST,
   after the overnight n8n run). Vercel sends `Authorization: Bearer $CRON_SECRET`
   automatically.
4. Pages use ISR (`revalidate = 3600`): visitors get cached HTML, data
   refreshes hourly.

## Database

`../supabase/migrations/` owns the schema. Everything there is already applied to production, apart from the optional `0016`, and its header says so. To change production, back up first and add the next numbered file.

The site reads with the public anon key, which can only read the market tables. `/btc`, `/audit` and `/api/snapshot` also use the service role, on the server only.

## Entering data by hand

There's no admin page, by decision. Use the Supabase table editor. The unique constraint and name check stop duplicates and typos.
